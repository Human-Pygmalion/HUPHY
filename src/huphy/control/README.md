# `control/` — 제어 루프

```
control/
├── loop.py      정해진 주기로 한 사이클씩 돌림
├── motions.py   매 주기 무엇을 시킬지 정함
├── policy.py    학습한 정책을 Motion 으로 만듦
├── rsl_rl.py    체크포인트(.pt) -> 부를 수 있는 함수. numpy 만 씀
└── POLICY.md    정책 실행 -- 실행 방법, 제한사항, 앞으로 바꿀 것
```

---

## 둘을 나눔

**루프는 무엇을 시킬지 모름.** 주기와 안전만 봄.

```
loop.py      주기, 모드, 시작·종료 순서, 밀림 측정
motions.py   (시간, 관찰) -> 관절 목표
policy.py    (시간, 관찰) -> 관절 목표.  안에서 모델을 부름
```

같은 루프로 유지·계단·사인파·보행 궤적을 다 돌릴 수 있고, **동작은 하드웨어 없이
시험됨** — 순수 함수라 그냥 부르면 됨.

## `loop.py`

### 한 사이클

```
1  목표를 정함        Motion 이 냄
2  계산               로봇이 관절 -> 모터 -> 프레임으로 풂
3  전송
4  수거               상태 갱신
5  기록               텔레메트리
6  다음 주기까지 기다림
```

### 두 가지 모드

| | 하는 일 |
|---|---|
| `OBSERVE` | 들어갈 때 **토크를 끊고** 상태만 읽음 |
| `CONTROL` | 토크를 넣고 명령을 보냄 |

`OBSERVE` 가 토크를 끊는 것은 **하드 안전장치**임. 설정이 잘못돼 있어도 다리가 안
움직이게 함 — 관찰하려고 켰는데 움직이면 안 됨.

동작을 넘겨도 **`OBSERVE` 는 무시함.**

### 관찰 모드도 통신을 함

MIT 프로토콜에는 **읽기 전용 명령이 없음.** 아무것도 보내지 않으면 아무것도 오지
않음.

그래서 `OBSERVE` 는 `robot.refresh()` 를 부름 — 게인과 토크가 0인 명령을 보내고
그 응답을 받음. 토크가 0이라 아무 일도 일어나지 않음.

### 기다리는 법

기다리는 방법이 둘임.

| | 하는 일 | 정확도 | CPU |
|---|---|---|---|
| **잠자기** `time.sleep` | 운영체제에 "N초 뒤 깨워줘" | 늦게 깨어남 | 안 씀 |
| **스핀** | 안 자고 시계만 계속 봄 | 정확 | 계속 씀 |

잠자기가 늦는 이유: 운영체제가 여러 프로그램을 번갈아 돌리는데 **깨워 주는 타이밍이
정해진 간격**임. 그 사이에 껴서 밀림. 100Hz 면 한 주기가 10ms 인데 거기에 1~2ms 가
섞이면 주파수가 눈에 띄게 떨어짐.

**둘을 섞음.** 대부분 자고 마지막만 시계를 봄.

```
남은 시간 > 3ms   ->  (남은 시간 - 3ms) 만큼 잠
남은 시간 <= 3ms  ->  돌면서 마감을 봄
```

100Hz 한 주기(10ms)로 보면:

```
7ms 잠자기      CPU 안 씀
1ms 시계 보기   CPU 씀        <- 한 주기당 이만큼만 태움
2ms 작업
```

### 여유(`sleep_margin`)가 잠의 오차보다 커야 함

여유가 작으면 **한 번의 긴 잠이 마감을 지나쳐 버려 스핀할 구간이 없어짐.**

```
여유 1ms:  남은 10ms -> 9ms 요청 -> 실제 10.9ms 잠 -> 이미 0.9ms 지남   스핀 못 함
여유 3ms:  남은 10ms -> 7ms 요청 -> 실제  8.9ms 잠 -> 1.1ms 남음        스핀으로 정확히
```

재보니 잠의 오차가 약 1.9ms 라 3ms 로 잡음.

재본 결과 (목표별 평균 오차):

| threshold/margin | 20ms | 10ms | 5ms | 2ms |
|---|---|---|---|---|
| 2ms / 1ms | +2.56 | +0.85 | +0.02 | +0.00 |
| **3ms / 3ms** | +0.61 | **+0.00** | +0.00 | +0.00 |
| 5ms / 5ms | +0.00 | +0.00 | +0.00 | +0.00 |

3ms 로 100Hz 이하에서 오차가 사라짐. 실제 스핀은 한 주기당 약 1ms 임.

루프 전체로 재면:

| 목표 | `precise=False` | `precise=True` |
|---|---|---|
| 50Hz | 43.4Hz | 48.6Hz |
| 100Hz | 84.7Hz | **99.9Hz** |
| 200Hz | 164.1Hz | **200.0Hz** |

### `precise` 가 하는 일

이 하나임.

```python
ControlLoop(leg, hz=100.0, precise=True)    # 섞어서 기다림  (기본)
ControlLoop(leg, hz=100.0, precise=False)   # 그냥 잠만 잠
```

**끄는 경우**: CPU 가 빠듯할 때. 파이에서 양다리와 텔레메트리를 같이 돌리는데
모자라면 끔.

**켜 두는 것이 기본인 이유**: 잠이 정확한 환경에서는 스핀 구간이 **저절로 짧아짐.**
8ms 요청에 8.1ms 만에 깨면 스핀은 0.1ms 뿐이라 손해가 없음.

리눅스는 잠이 더 정확하므로, 파이에서 `precise=False` 로도 목표 주파수가 나오면
굳이 켤 필요 없음.

시계는 `time.perf_counter()` 를 씀 — 해상도가 가장 높음.

### 마감을 절대 시각으로 들고 있음

매 주기 "남은 시간" 을 새로 계산하면 그 오차가 쌓여 서서히 밀림.

### 실제 주기를 잼

목표 주기와 실제 주기는 다름. 계산이 길어지거나 수거가 늦어지면 밀림.

**두 가지를 따로 봄.**

| | 무엇을 잡나 |
|---|---|
| `overruns` | 튀는 주기. 목표의 1.5배를 넘긴 횟수 |
| `kept_up` | **꾸준히 느린 것.** 평균이 목표의 90% 미만 |

둘이 다름 — 매 주기 24%씩 넘으면 **한 번도 "밀림" 으로 세지 않으면서** 주파수만
떨어짐. 그것을 `kept_up` 이 잡음.

```
51주기 0.6초 (평균 84.8Hz / 목표 100Hz), 밀림 0회, 최악 12.5ms,
무응답 주기 5회  ** 주기를 못 지킴 **
```

**게인을 만지기 전에 이것부터 볼 것.** 주기가 밀리는데 게인을 튜닝하면 게인이
아니라 주기가 문제인데 게인을 계속 만지게 됨.

`loop_dt` 는 매 주기 텔레메트리로도 나감.

### 밀려도 따라잡지 않음

늦은 만큼 다음 주기를 줄여 따라잡으면 **그 주기가 더 짧아져 계산이 또 밀림.**
한 주기를 늦게 시작하고 마는 편이 나음.

### 멈출 때

```
1  게인을 유지한 채 현재 자세를 목표로 (hold) — 5주기
2  토크 차단
3  텔레메트리 flush
```

**바로 토크를 끊지 않음.** 서 있는 다리에서 힘이 갑자기 빠지면 주저앉음.

**끝나는 경로가 하나임.** 정상 종료든 예외든 `finally` 를 지나며 이 순서를 탐.
자세 유지가 실패해도 토크는 반드시 끊음.

### 한 걸음씩

```python
loop.step(motion, t=0.0)     # 기다리지 않음
```

한 사이클만 떼어 시험하거나 대화형으로 돌릴 때 씀. 주기 유지는 `run` 이 함.

## `motions.py`

전부 **함수를 만드는 함수**임. 하드웨어도 CAN 도 모름.

```python
(경과 시간 초, 지금 관찰) -> {관절 이름: 목표 각도}  또는  None
```

`None` 을 내면 그 주기는 명령을 보내지 않음.

| | 무엇 |
|---|---|
| `hold(targets)` | 정해진 자세를 계속 보냄 |
| `freeze(joints)` | **첫 주기의 실측 위치**를 잡고 유지 |
| `step(joint, ...)` | 정해진 시각에 목표를 한 번에 옮김 |
| `sine(joint, ...)` | 왕복 |
| `ramp(joint, ...)` | 정해진 시간에 걸쳐 천천히 |
| `chain((m, 초), ...)` | 순서대로 이음 |

### `freeze` 가 따로 있는 이유

`hold` 는 목표를 미리 정하지만 `freeze` 는 **다리가 지금 있는 자리**를 씀.

목표를 0으로 잡고 제어를 시작하면 토크를 넣는 순간 다리가 0을 향해 한 번에
움직임. 제어 시작 직후 첫 동작으로 씀.

### `chain` 은 각 구간의 0초부터 셈

```python
motions.chain(
    (motions.ramp("knee", start=0.0, end=30.0, seconds=2.0), 2.0),
    (motions.sine("knee", center=30.0, amplitude=5.0, hz=0.5), 10.0),
)
```

이어 붙일 때마다 시간 계산을 다시 하지 않아도 됨. 마지막이 끝나면 `None` 을 냄.

## 게인 튜닝

### 순서

```
1  loop_dt 부터 확인      주기를 못 지키면 게인 문제가 아님
2  hold 로 시작           자세가 유지되나, 처지나, 떨리나
3  step 으로 계단 응답     여기서 대부분이 결정됨
4  sine 으로 확인          추종 지연과 진폭 감쇠
```

### 계단 응답에서 읽는 것

```python
motions.step("knee", start=0.0, end=30.0, at_s=1.0)
```

| 그래프 | 뜻 | 할 것 |
|---|---|---|
| 목표까지 못 감 | `kp` 부족 | `kp` 올림 |
| 지나쳤다 돌아옴 | `kd` 부족 | `kd` 올림 |
| 부르르 떨림 | `kp` 과함 | `kp` 내림 |
| 느리게 도달 | 여유 있음 | `kp` 올릴 수 있음 |

**계단 직전이 평평해야 오버슛을 읽을 수 있음.** `at_s` 로 여유를 두는 이유임 —
시작하자마자 뛰면 초기 과도상태와 섞임.

### 계단이 그대로 안 나감

**점프 가드가 자름.** 한 주기에 `max_delta_deg` 까지만 가므로 실제로는 몇 주기에
걸쳐 올라감. 그 기울기가 속도 상한임.

`right_leg/guard/clip_jump` 가 오르는 것으로 확인됨. 계단 응답을 제대로 보려면
`max_delta_deg` 를 충분히 크게 두거나, `ramp` 로 대신할 것.

### 토크가 상한에 붙었는지

`tau` 가 모터 상한(RS02 17 N·m, RS00 14 N·m)에 붙어 있으면 **`kp` 를 올려도
소용없음.** 이미 낼 수 있는 힘을 다 내고 있음.

기구를 바꾸거나 목표를 낮춰야 함.

### 한 관절씩

```python
motions.step("knee", start=0.0, end=30.0, hold_others={"hip_pitch": -50.0})
```

나머지는 붙잡아 둠. 여럿을 같이 흔들면 **어느 관절이 원인인지 섞임.**

## 쓰는 법

```python
from huphy.control import ControlLoop, Mode, motions

loop = ControlLoop(leg, hz=robot_config.limb("right_leg").control_hz,
                   telemetry=tm, mode=Mode.CONTROL)

motion = motions.chain(
    (motions.freeze(["knee"]), 0.5),                              # 지금 자리를 잡고
    (motions.step("knee", start=0.0, end=30.0, at_s=0.5), 3.0),   # 계단
)
stats = loop.run(motion, duration_s=4.0)
print(stats.summary())
```

`stop()` 으로 다른 스레드나 시그널 처리기에서 멈출 수 있음.

## `policy.py`

학습한 정책을 `Motion` 으로 만듦. 모양이 같아서 `loop.run()` 에 그대로 들어감.

```python
motion = policy.policy_motion(model, imu, spec=policy.BALANCE)
loop.run(motion)
```

**모델은 관절 이름을 모름.** 정해진 순서의 숫자 벡터를 받고 같은 순서로 냄. 그
순서와 단위를 정하는 것이 이 파일의 일임.

```python
JOINT_ORDER = ("hip_pitch", "hip_roll", "hip_yaw", "knee", "ankle_pitch", "ankle_roll")
#              id 7        id 8        id 9       id 10   id 11 + id 12 로 풀림

MOTOR_ORDER = ("hip_pitch", "hip_roll", "hip_yaw", "knee", "ankle_a", "ankle_b")
#              앞 네 칸은 같음                              id 11      id 12 로 그대로
```

### 발목이 두 갈래임

시뮬이 발목을 두 축 관절로 두느냐 두 모터로 두느냐에 따라 모델이 내는 마지막 두
칸이 다름. 어느 쪽인지는 **실행할 때 인자로 고름** (`huphy-run --ankle-space`).

| | 모델이 내는 것 | 실물에서 |
|---|---|---|
| `rp` | 발판 자세 (pitch/roll) | IK 를 거쳐 모터각으로 |
| `ab` | 모터 각도 | 그대로 나감 |

`PolicySpec` 에 안 넣은 이유: `action_scale` 도 `obs_dim` 도 두 공간이 똑같아서,
규격에 넣으면 같은 모델이 `balance_rp`/`balance_ab` 로 둘씩 늘어날 뿐임.

**어긋나도 코드로는 안 잡힘.** 관찰 개수도 행동 개수도 같아 가중치 검사를 그냥
통과함. 사람이 맞게 골라야 하고, `huphy-run` 이 시작 화면에 찍음.

받는 쪽(`Leg`)은 인자를 안 받음 — **들어온 이름을 보고** 갈림. 플래그를 따로 들면
명령과 그 해석이 어긋날 수 있는데, 명령 자체가 어느 공간인지 말해 주면 어긋날
수가 없음.

### 관찰

시뮬(mjlab)이 이 순서로 이어 붙임. 가중치 파일의 입력 차원과 맞음.

```
base_ang_vel        3    IMU 각속도 (rad/s)
projected_gravity   3    중력 방향을 몸체 좌표로. IMU 모듈이 만들어 올림
joint_pos           6    관절 각도 (rad)
joint_vel           6    (rad/s)
actions             6    직전 주기에 낸 행동 그대로
hop_phase           2    sin/cos.  hopping 에만

balance  24        hopping  26
```

`actions` 가 **관절 목표가 아니라 모델 출력 그대로**임. `action_scale` 을 곱하기
전의 값이라 정책이 자기가 낸 것을 그대로 다시 봄.

`hop_phase` 를 각도가 아니라 `sin`/`cos` 로 주는 이유: 한 바퀴 돌 때 값이 튀지
않음.

### 행동

```
관절 목표 = 기본 자세 + action_scale x 행동
```

기본 자세가 전부 0 이라 두 번째 항만 남음. `action_scale` 은 balance 0.25,
hopping 0.5 임 — 시뮬 설정에서 그대로 옮긴 값.

### 단위

```
저장소   도, 도/초
모델     라디안, rad/s
```

여기서 바꿈. 모델 경계가 단위가 갈리는 유일한 자리임.

### 정규화는 모델 쪽에서

학습 중에 쌓인 평균·표준편차가 가중치 파일에 들어 있음.

```
정규화된 입력 = (관찰 - mean) / std
```

**빼먹으면 모델이 전혀 다르게 동작함.** `policy.py` 는 정규화까지 끝난 벡터를
받는 것을 모델로 봄 — 프레임워크(torch 등)를 가리지 않으려는 것임.

### 발목만 다르게 풀림

```
id 7~10   모델이 낸 각도를 그 모터에 그대로
id 11,12  ankle_pitch/ankle_roll -> 기구학을 거쳐 모터로
```

시뮬에서는 발목 두 축이 독립 관절이고 각자 서보가 붙어 있음. 실물은 모터 두 개가
로드로 둘을 같이 만들어서, `Leg` 가 `ankle_output` 에 따라 각도나 토크로 내려보냄.
