# RobStride 모터 초기 설정 — 출하 상태에서 쓸 수 있는 상태까지

**갓 뜯은 모터를 이 저장소가 다룰 수 있게 만드는 절차임.**

루트 README 는 이게 끝난 상태를 전제함 — 거기서부터는 `huphy-commission` 으로 관절
이름을 부르면 됨. 여기는 그 이전임.

    출하 상태            private 프로토콜, CAN id 0x7F, 1 Mbps, 호스트 id 0xFD
    이 저장소가 쓰는 것  MIT 프로토콜, CAN id 1~6(왼다리) 7~12(오른다리), zero_sta = 1,
                         호스트 id = 0xF0 + CAN id, 펌웨어는 Command 14 를 받는 판

**이 단계에서는 `huphy-commission` 을 못 씀.** 그 도구는 `robot.yaml` 에 적힌 id 로만
프레임을 보내는데, 출하 상태 모터는 그 id 를 안 쓰고 프레임 형식도 다름. 그래서
여기서는 `cansend` 로 직접 보냄.

출처는 각 모델의 RobStride 사용자 매뉴얼임. RS02·RS03·RS04 의 명령 표가 글자까지
같음.

---

## 빠른 참조

`<DD>` 는 대상 모터 id, **16진수**임. 출하 상태는 `7F`, 부여한 뒤에는 그 id.
`<NN>` 은 새로 줄 id. 10번은 `0A`, 12번은 `0C`.

```bash
cansend can1 0000FD<DD>#0000000000000000        # Type 0   호출. 살아 있나
cansend can1 07<NN>FD<DD>#0000000000000000      # Type 7   id 를 <NN> 으로    즉시
cansend can1 1200FD<DD>#2970000001000000        # Type 18  zero_sta -> 1     RAM 에만
cansend can1 1600FD<DD>#0102030405060708        # Type 22  플래시 저장
cansend can1 1900FD<DD>#0102030405060200        # Type 25  프로토콜 -> MIT    재투입
# 여기부터 MIT (3자리 id)
cansend can1 <DDD>#FFFFFFFFFFFF<HH>01           # Command 9  호스트 id -> <HH> = F0+id  즉시·영구
cansend can1 3<DD>#1C70000000000000             # Command 14 VBUS 읽기. 답이 없으면 15절(펌웨어)
python3 tools/can_scan.py                       # 전체 확인
```

응답은 `candump -x can1` 의 `RX` 줄만 봄. 자세한 것은 아래 절.

## 1. 전제

```bash
sudo apt install -y can-utils
```

### 채널 올리기

**어댑터 종류에 따라 다름.** 속도를 어디서 정하느냐가 갈림길임.

```bash
# USB 어댑터 (CANable 등) -- 속도를 어댑터가 들고 있음
sudo slcand -o -c -s8 /dev/canable0 can1
sudo ip link set can1 up

# 네이티브 CAN (HAT, MCP2515) -- 속도를 커널이 들고 있음
sudo ip link set can1 up type can bitrate 1000000
```

`-s8` 이 **1 Mbps** 임. 모터 출하 기본값이 1 Mbps 라 이대로 맞음.

USB 쪽은 `can1` 이 **찾는 이름이 아니라 짓는 이름**임 -- `slcand` 마지막 인자가
만들어낼 장치 이름이고, `config/robot.yaml` 의 `channel` 과 같아야 함. 네이티브
쪽은 부팅할 때 드라이버가 이미 만들어 두므로 골라 쓸 수 없음.

이 문서의 명령은 모두 `can1` 로 씀. 1.0 다리는 `canr`(오른다리) / `canl`(왼다리)
이므로 그 이름으로 바꿔 넣을 것.

```bash
ip -br link show type can        # 지금 뭐가 있나
ip -details link show can1       # state UP 이 보여야 함
```

`/dev/canable0` 은 udev 로 고정한 심볼릭 링크임. USB 는 꽂는 순서대로 `ttyACM0`,
`ttyACM1` 이 붙어 재부팅마다 달라짐. 자세한 것은 루트
[README](../README.md) 4번.

### 한 대씩

**모터를 한 대만 물릴 것.** 출하 상태는 전부 같은 id 라, 여러 대를 물리면 명령이
양쪽에 다 가고 응답도 같이 나와서 어느 쪽인지 구분이 안 됨. 그 상태가 되면 선을
뽑는 것 말고 되돌릴 방법이 없음.

## 2. 순서

```
1  지금 id 찾기        Type 0        private
2  id 부여              Type 7        private, 즉시 적용
3  zero_sta 를 1 로     Type 18 + 22  private, 저장 필요
4  프로토콜 -> MIT       Type 25       private, 전원 재투입 후 적용
5  전원 재투입
6  확인                 MIT 표준 프레임에 답하는지
7  호스트 id 를 F0+id 로  Command 9     MIT, 즉시·영구          (14절)
8  펌웨어 확인           Command 14     답이 없으면 업데이트     (15절)
9  선을 빼고 다음 모터
```

**프로토콜을 맨 마지막에 바꿈.** 1~3 이 전부 private 확장 프레임이라, 먼저 MIT 로
넘기면 그 셋을 못 씀. 그리고 재투입하는 순간 id 가 이미 맞으므로
`huphy-commission` 이 바로 붙음.

## 3. 프레임 규격

**여기부터 나오는 모든 명령은 이 두 틀 중 하나임.** 자리마다 무엇을 넣는지만 바꿈.

### private — 29-bit 확장 프레임

출하 상태에서 쓰는 형식임. `cansend` 는 id 를 **8자리**로 쓰면 확장 프레임임.

```
cansend can1 TTNNHHDD#<데이터 16자리>
             ││││
             ││││
             │││└── DD  대상 모터 id
             ││└─── HH  호스트 id
             │└──── NN  타입마다 다름. 대부분 00
             └───── TT  통신 타입
```

| TT | 타입 | NN | 데이터 16자리 | 무엇 |
|---|---|---|---|---|
| `00` | 0 | `00` | `0000000000000000` | 지금 id 물어보기 |
| `07` | 7 | **새 id** | `0000000000000000` | CAN id 부여. 즉시 |
| `11` | 17 | `00` | `<인덱스>0000<값>` | 파라미터 읽기 |
| `12` | 18 | `00` | `<인덱스>0000<값>` | 파라미터 쓰기. RAM 에만 |
| `16` | 22 | `00` | `0102030405060708` | 플래시에 커밋 |
| `19` | 25 | `00` | `010203040506<PP>00` | 프로토콜 전환. 재투입 |

### MIT — 11-bit 표준 프레임

프로토콜을 바꾼 뒤에 쓰는 형식임. id 를 **3자리**로 쓰면 표준 프레임임.

```
cansend can1 DDD#FFFFFFFFFFFFFFCC
             │                ││
             │                │└── CC  명령 코드
             │                └─── FF  F_CMD. 명령마다 다름
             └──────────────────── DDD 대상 모터 id, 3자리
```

| CC | 명령 | F_CMD | 무엇 |
|---|---|---|---|
| `FC` | 1 | `FF` | 토크 켜기 |
| `FD` | 2 | `FF` | 정지. 살아 있는지 볼 때 씀 |
| `FA` | 7 | **새 id** | CAN id 부여 |
| `FD` | 8 | **프로토콜** | 프로토콜 전환 |
| `01` | 9 | **새 호스트 id** | 응답 프레임의 CAN id 를 바꿈 (14절) |

`FD` 가 두 번 나오는데 `F_CMD` 로 갈림 — `FF` 면 정지, 다른 값이면 프로토콜 전환임.

**파라미터 읽기(Command 14)는 틀이 다름.** 11비트 id 의 위 3비트에 명령 번호가 들어감.

```
cansend can1 3DD#<인덱스>000000000000
             │
             └── 3 = 읽기. 7번 모터면 307, 10번이면 30A
```

응답은 `<인덱스>0000<값 4바이트>` 이고, 값은 하위 바이트 먼저임. **0x70xx 표만
읽힘** -- 0x30xx 관측 표(온도 등)와 0x1003 버전은 0 만 돌아옴. 온도는 상태 프레임에
늘 실려 오므로 따로 읽을 필요가 없음.

### 자리에 넣는 값

| 자리 | 값 |
|---|---|
| `DD` / `DDD` 대상 모터 id | 출하 상태는 `7F` / `07F`. 부여한 뒤에는 그 id |
| `HH` 호스트 id | private 요청에는 `FD` 를 실어 보냄. MIT 응답이 오는 id 는 모터에 저장된 호스트 id (14절, `F0`+모터 id) |
| `PP` 프로토콜 | `00` private / `01` CANopen / `02` **MIT** |
| 인덱스 | 파라미터 번호를 **하위 바이트 먼저**. `0x7029` -> `2970` |
| 값 | 4바이트, **하위 바이트 먼저**. 1 -> `01000000` |

### id 는 16진수임

`config/robot.yaml` 에는 10진수로 적혀 있는데 **프레임에는 16진수로 들어감.**
7~9 까지는 같아 보이다가 10부터 갈라짐.

| 관절 | `robot.yaml` | 확장 `DD` | 표준 `DDD` |
|---|---|---|---|
| hip_pitch | 7 | `07` | `007` |
| hip_roll | 8 | `08` | `008` |
| hip_yaw | 9 | `09` | `009` |
| knee | **10** | **`0A`** | **`00A`** |
| ankle_a | **11** | **`0B`** | **`00B`** |
| ankle_b | **12** | **`0C`** | **`00C`** |

왼다리는 1~6 이라 `01`~`06` / `001`~`006` 임. 출하 상태는 127 이라 `7F` / `07F`.

**`010` 이라고 치면 16번 모터에게 보내는 것임.** 그런 모터가 없으니 응답이 없고,
원인이 배선처럼 보임.

### 표준 프레임은 3자리를 채울 것

`cansend` 는 **자릿수로 프레임 형식을 정함.**

```
3자리   표준 프레임 (11-bit)   MIT
8자리   확장 프레임 (29-bit)   private
```

id 가 작아도 앞을 0 으로 채워야 함. `7#...` 처럼 쓰면 형식이 안 잡힘.

```bash
cansend can1 007#FFFFFFFFFFFFFFFD     # id 7   hip_pitch
cansend can1 00A#FFFFFFFFFFFFFFFD     # id 10  knee
```

## 4. 지금 id 찾기 — Type 0

```bash
candump -x can1 &                               # -x 가 RX/TX 를 구분해 줌
cansend can1 0000FD<DD>#0000000000000000        # <DD> = 물어볼 id. 출하 상태면 7F
```

출하 상태 모터 하나면:

```bash
cansend can1 0000FD7F#0000000000000000
```

### `-x` 를 붙일 것

**`candump` 는 자기가 보낸 프레임도 같이 보여줌.** socketcan 은 로컬 루프백이
기본이라 `cansend` 로 내보낸 것이 그대로 화면에 뜸.

`-x` 없이 보면 보낸 것과 받은 것이 섞여서, **모터가 답을 안 해도 뭔가 오는 것처럼
보임.**

```
can1  TX  0000FD7F  [8]  00 00 00 00 00 00 00 00     <- 내가 보낸 것
can1  RX  00007FFE  [8]  41 54 90 07 E8 0C 08 05     <- 모터가 답한 것
```

**`RX` 가 하나도 없으면 모터가 아무 답도 안 한 것임.**

### 응답 읽는 법

응답은 항상 `0000<모터 id>FE` 모양임.

```
can1  RX  00007FFE  [8]  41 54 90 07 E8 0C 08 05
          ────┬───       ────────┬────────
              │                  └── 64-bit MCU 고유번호
              00 00 7F FE
               │  │  │  └── FE   Type 0 응답 표시 (고정)
               │  └──┴───── 7F   **모터 id. 여기를 읽음**
               └─────────── 00   통신 타입 0
```

**보낸 프레임과 자리가 다름.**

```
보냄    0000FD7F      FD = 호스트,  7F = 대상 모터
응답    00007FFE      7F = 모터 id, FE = 응답 표시
```

데이터는 MCU 고유번호라 id 확인에는 안 씀. 다만 **같은 값이 두 줄 나오면 모터가 두
대 물려 있는 것**이므로 그건 봐 둘 만함 — 한 대만 남기고 다시 함.

### id 를 모르면 훑음

```bash
for i in $(seq 0 127); do
  printf -v id "0000FD%02X" $i                  # 마지막 두 자리가 <DD>
  cansend can1 "$id#0000000000000000"
  sleep 0.02
done
```

`RX` 로 뜬 `0000<id>FE` 의 가운데가 그 모터의 id 임.

## 5. id 부여 — Type 7

```bash
cansend can1 07<NN>FD<DD>#0000000000000000
#              │     └── DD  지금 id. 출하 상태면 7F
#              └──────── NN  새로 줄 id
```

무릎(0x0A)으로 만들 때:

```bash
cansend can1 070AFD7F#0000000000000000          # Type 7  0x7F -> 0x0A
```

**이 명령만 id 가 두 개 들어감.** 앞이 새 id, 뒤가 지금 id 임.

관절별로는 `NN` 자리만 바뀜. **10진수가 아니라 16진수임** (3절).

| 관절 | 오른 id | 오른 프레임 | 왼 id | 왼 프레임 |
|---|---|---|---|---|
| hip_pitch | 7 | `0707FD7F` | 1 | `0701FD7F` |
| hip_roll | 8 | `0708FD7F` | 2 | `0702FD7F` |
| hip_yaw | 9 | `0709FD7F` | 3 | `0703FD7F` |
| knee | 10 | `070AFD7F` | 4 | `0704FD7F` |
| ankle_a | 11 | `070BFD7F` | 5 | `0705FD7F` |
| ankle_b | 12 | `070CFD7F` | 6 | `0706FD7F` |

10·11·12 가 `0A`·`0B`·`0C` 로 들어가는 자리임.

### 응답

```
can1  TX  070AFD7F  [8]  00 00 00 00 00 00 00 00     <- 보낸 것. 에코
can1  RX  00000AFE  [8]  41 54 90 07 E8 0C 08 05     <- 0x0A 로 바뀜. 성공
```

**즉시 적용됨.** 재투입이 필요 없음. 확인은 **새 id** 로 4절을 다시 함.

```bash
cansend can1 0000FD<NN>#0000000000000000        # Type 0  <NN> = 방금 준 id
```

무릎이면:

```bash
cansend can1 0000FD0A#0000000000000000          # Type 0  0x0A 에게
```

**여기 들어가는 것이 옛 id 가 아니라 새 id 임.** 바뀌었는지 보는 것이므로 새 id 가
답해야 성공임.

| `RX` 로 뜨는 것 | 뜻 |
|---|---|
| `0000<NN>FE` | 새 id 로 바뀜. 성공 |
| 없음 | 옛 id 로 물어볼 것 |

```bash
cansend can1 0000FD7F#0000000000000000          # Type 0  옛 id 에게
```

옛 id 가 답하면 변경이 안 된 것이고, 양쪽 다 없으면 배선·전원 문제라 id 얘기가
아님.

## 6. `zero_sta` 를 1 로 — Type 18 + Type 22

기본값이 0 이면 위치를 `[0, 2π)` 로 보고함. 이 저장소는 `[-π, π)` 를 전제하므로
1 로 바꿔야 함 — 안 바꾸면 음수 각도가 340도 같은 값으로 나옴.

```bash
cansend can1 1200FD<DD>#2970000001000000        # Type 18  쓰기
cansend can1 1600FD<DD>#0102030405060708        # Type 22  저장
```

무릎이면:

```bash
cansend can1 1200FD0A#2970000001000000
cansend can1 1600FD0A#0102030405060708
```

### 데이터 자리

```
2970 0000 01000000
 │    │    └── 값 1. 4바이트, 하위 바이트 먼저
 │    └─────── 고정 00 00
 └──────────── 파라미터 0x7029. **하위 바이트 먼저**
```

`0x7029` 를 `2970` 으로 뒤집어 쓰는 것이 걸리는 자리임.

### 응답

**둘 다 Type 2(피드백) 프레임으로 답함.** 4·5절의 `0000<id>FE` 와 다른 모양임.

```
can1  TX  1200FD0A  [8]  29 70 00 00 01 00 00 00     <- Type 18 보냄
can1  RX  02000AFD  [8]  85 53 80 08 5F 01 00 FA     <- 피드백
          ──┬─────       ──┬── ──┬── ──┬── ──┬──
            │               │     │     │     └── 온도 x10.  00FA = 25.0도
            │               │     │     └──────── 토크
            │               │     └────────────── 속도
            │               └──────────────────── 현재각
            02 00 0A FD
             │  │  │  └── FD   호스트 id. 우리가 보낸 값이 되돌아옴
             │  │  └───── 0A   답하는 모터 id
             │  └──────── 00   모드·고장 비트. 00 이면 Reset 모드, 고장 없음
             └─────────── 02   통신 타입 2
```

**Type 22 는 Type 0 형식으로 답함.**

```
can1  TX  1600FD0A  [8]  01 02 03 04 05 06 07 08     <- Type 22 보냄
can1  RX  00000AFE  [8]  41 54 90 07 E8 0C 08 05     <- Type 0 형식
```

매뉴얼에는 Type 22 도 Type 2 피드백으로 답한다고 적혀 있는데 **실물은 Type 0 로
답함.** 관측을 따름.

| `RX` 로 뜨는 것 | 뜻 |
|---|---|
| `0000<DD>FE` | 저장 명령이 전달됨 |
| `0200<DD>FD` | 같음. 펌웨어에 따라 이쪽으로 올 수도 있음 |
| 없음 | id 가 틀렸거나 배선·전원 |

**응답이 왔다는 것은 명령이 전달됐다는 뜻까지임.** 값이 실제로 써졌는지는 Type 17
로 읽어서 봐야 함 (아래).

### Type 22 가 왜 필요한가

매뉴얼의 Type 18 제목이 **"Single parameter write (lost in power failure)"** 임.
쓰면 그 순간부터 동작은 바뀌는데 RAM 에만 있음.

```
Type 18 만    ->  지금은 1. 재투입하면 0 으로 돌아감
Type 18 + 22  ->  재투입해도 1
```

Type 22 는 데이터 `0102030405060708` 이 고정값임 — 대상이나 값을 고르는 칸이 아니라
**그때까지 쓴 것을 통째로 커밋**하는 명령임. 여러 파라미터를 바꿀 거면 마지막에 한
번만 보냄.

### 확인 — Type 17

```bash
cansend can1 1100FD<DD>#2970000000000000        # Type 17  읽기
```

무릎이면:

```bash
cansend can1 1100FD0A#2970000000000000
```

**Type 17 은 응답도 Type 17 인데 호스트와 모터 자리가 바뀜.**

```
can1  TX  1100FD0A  [8]  29 70 00 00 00 00 00 00
              ──┬── ─┬                                  FD = 호스트,  0A = 대상 모터
can1  RX  11000AFD  [8]  29 70 00 00 01 00 00 00
              ──┬── ─┬   ──┬── ──┬── ─┬
                │     │     │     │    └── Byte4  읽은 값. 01 이면 됨
                │     │     │     └─────── Byte2~3  고정 00 00
                │     │     └───────────── Byte0~1  파라미터 0x7029
                │     └── FD   호스트 id
                └──────── 0A   답하는 모터 id
```

보낼 때는 `...FD0A`(호스트 → 모터)이고 받을 때는 `...0AFD`(모터 → 호스트)임.
**두 바이트가 뒤집혀 돌아옴.**

| `Byte4` | 뜻 |
|---|---|
| `01` | `zero_sta` 가 1 임. 성공 |
| `00` | 안 써졌거나 Type 22 가 이 파라미터에 안 먹음 |

재투입 후에 한 번 더 읽어야 **저장까지 됐는지** 확인됨. 쓰기 직후에 읽으면 RAM
값이라 Type 22 가 실패해도 `01` 이 나옴.

## 7. 프로토콜을 MIT 로 — Type 25

```bash
cansend can1 1900FD<DD>#010203040506<PP>00
#                                    └── PP  00 private / 01 CANopen / 02 MIT
```

무릎을 MIT 로:

```bash
cansend can1 1900FD0A#0102030405060200
```

```
can1  TX  1900FD0A  [8]  01 02 03 04 05 06 02 00     <- 보낸 것
can1  RX  00000AFE  [8]  41 54 90 07 E8 0C 08 05     <- Type 0 형식 응답
```

응답이 왔다는 것은 **명령이 전달됐다**는 뜻이지 프로토콜이 바뀌었다는 뜻이 아님.
바뀐 것은 재투입 후에 확인함 (8절).

| `RX` 로 뜨는 것 | 뜻 |
|---|---|
| `0000<DD>FE` | 전환 명령이 전달됨. 재투입해야 적용 |
| 없음 | id 가 틀렸거나 배선·전원 |

**전원을 재투입해야 적용됨.** 재투입 전까지는 확장 프레임으로 계속 통신해야 함.

## 8. 전원 재투입 후 확인

MIT 는 11-bit **표준** 프레임임. 정지 명령(Command 2)을 보내 답하는지 봄.

```bash
cansend can1 <DDD>#FFFFFFFFFFFFFFFD             # <DDD> = 대상 모터 id. 16진수 3자리
```

**id 10 은 `010` 이 아니라 `00A` 임** (3절). 무릎이면:

```bash
cansend can1 00A#FFFFFFFFFFFFFFFD
```

**`RX` 가 3자리 id 로 오면 MIT 임.** 응답의 id 는 모터 id 가 아니라 **호스트 id** 임 --
출하 상태 그대로면 `0FD`, 14절을 마쳤으면 `0F0`+모터 id (무릎이면 `0FA`).

```
can1  TX  00A       [8]  FF FF FF FF FF FF FF FD     <- 보낸 것. 에코
can1  RX  0FD       [8]  0A 85 53 80 08 5F 01 3A     <- 표준 프레임. MIT
                         ─┬ ──┬── ──┬── ─┬ ──┬──
                          │   │     │    │   └── 온도 x10
                          │   │     │    └────── 토크
                          │   │     └─────────── 속도
                          │   └───────────────── 현재각
                          └───────────────────── 모터 id 0x0A
```

Response Command 1(일반 상태 프레임)이라 `Byte0` 이 모터 id 임. 값이 실려 오므로
**모터가 실제로 돌고 있다는 것까지 확인됨.**

| `RX` 로 뜨는 것 | 뜻 |
|---|---|
| `0FD`·`0FA` 등 3자리 | MIT 로 바뀜. 성공 |
| `00000AFE` 8자리 | 아직 private. 재투입을 안 했거나 Type 25 가 안 먹음 |
| 없음 | id·배선·전원. 4절의 Type 0 로 되짚음 |

아직 private 인지 보려면 확장 프레임으로 물어봄.

```bash
cansend can1 0000FD0A#0000000000000000          # Type 0  확장 프레임으로
```

여기에 답하면 아직 private 임.

## 10. id 가 부여된 뒤의 조작

**MIT 로 바뀐 뒤에는** 이 저장소 도구를 씀. 프로토콜을 되돌리거나, 나중에 모터를
교체했을 때 쓰는 자리임.

```bash
huphy-commission --limb right_leg can-id knee --to 10 --yes
huphy-commission --limb right_leg protocol knee --to mit --yes
```

관절 이름 대신 CAN id 로도 부를 수 있음. 관절 이름을 빼면 목록을 보여주고 물어봄.

같은 조작을 손으로 보내려면 3절의 MIT 틀을 씀.

```bash
cansend can1 <DDD>#FFFFFFFFFFFF<NN>FA           # Command 7  <NN> = 새 id
cansend can1 <DDD>#FFFFFFFFFFFF<PP>FD           # Command 8  <PP> = 프로토콜
```

private 은 새 값이 **중재 id 안**에 들어가는데 MIT 는 **데이터 7번째 바이트** 에
들어감. 같은 조작인데 값이 놓이는 자리가 다름.

### 응답 형식이 다름

Command 7·8 의 응답은 **Response Command 2** 이고 일반 상태 프레임이 아님.

```
Response Command 1 (일반 상태)   Byte0 이 모터 id
Response Command 2 (MCU 식별)    11-bit 중재 id 가 모터 id, 데이터는 MCU 고유번호
```

모터 id 가 데이터가 아니라 중재 id 에 실림. 일반 상태 프레임처럼 `Byte0` 으로
판정하면 MCU 고유번호의 첫 바이트를 id 로 읽게 됨.

그래서 `set_can_id` 는 이 응답으로 판정하지 않고, **새 id 로 정지 명령을 보내 응답이
오는지**로 확인함.

`set_protocol` 은 바뀌었는지 확인하지 않음. 8절의 방법으로 사람이 확인해야 함.

## 11. 모델별 인코딩 범위

CAN 프레임에는 N·m 이 아니라 범위 안의 눈금만 실림. 설정의 `model` 이 실물과 다르면
그 비율만큼 토크가 어긋나는데 프레임도 응답도 정상임.

각 매뉴얼의 Command 3 "MIT Dynamic Parameters" 표에서 옮김.

| 모델 | 각도 16bit | 속도 12bit | Kp 12bit | Kd 12bit | 토크 12bit |
|---|---|---|---|---|---|
| RS00 | ±12.57 rad | ±33 rad/s | 0~500 | 0~5 | ±14 N·m |
| RS02 | ±12.57 rad | ±44 rad/s | 0~500 | 0~5 | ±17 N·m |
| RS03 | ±12.57 rad | ±20 rad/s | 0~5000 | 0~100 | ±60 N·m |
| RS04 | ±12.57 rad | ±15 rad/s | 0~5000 | 0~100 | ±120 N·m |

**각도만 네 모델이 같음.** 큰 모터일수록 속도 범위가 좁고 게인 범위가 넓음.

**게인이 제일 위험함.** RS02 표(`0~500`)로 RS04 에 `kp=20` 을 보내면 모터가 `199` 로
받음 -- 10배임. `kd` 는 20배가 됨. 토크는 RS02 설정으로 RS04 를 돌리면 시킨 것의
**7배**가 나감 (120/17).

private 프로토콜도 **범위는 같음.** 다른 것은 비트 폭뿐임 -- private 은 속도·토크가
16bit 이고 MIT 은 12bit 임.

## 12. 명령 한눈에

`<DD>` 자리에 대상 모터 id 를 넣음. 출하 상태면 `7F`, 부여한 뒤에는 그 id 임.

```bash
# 채널 -- 어댑터에 맞는 쪽 하나만
sudo slcand -o -c -s8 /dev/canable0 can1 && sudo ip link set can1 up  # USB 어댑터
sudo ip link set can1 up type can bitrate 1000000                     # 네이티브 CAN
candump -x can1 &                               # 응답을 지켜봄. -x 가 RX/TX 를 구분

# private -- 29-bit 확장 프레임 (id 8자리)
cansend can1 0000FD<DD>#0000000000000000        # Type 0   지금 id 확인
cansend can1 07<NN>FD<DD>#0000000000000000      # Type 7   id 를 <NN> 으로   즉시
cansend can1 0000FD<NN>#0000000000000000        # Type 0   새 id 로 확인
cansend can1 1200FD<NN>#2970000001000000        # Type 18  zero_sta -> 1     RAM 에만
cansend can1 1600FD<NN>#0102030405060708        # Type 22  플래시에 커밋
cansend can1 1100FD<NN>#2970000000000000        # Type 17  zero_sta 읽기     Byte4 = 01
cansend can1 1900FD<NN>#0102030405060200        # Type 25  프로토콜 -> MIT    재투입 필요

# 전원 재투입

# MIT -- 11-bit 표준 프레임 (id 3자리)
cansend can1 <DDD>#FFFFFFFFFFFFFFFD             # Command 2  정지. 응답 오면 MIT
cansend can1 <DDD>#FFFFFFFFFFFF<HH>01           # Command 9  호스트 id -> F0+id
cansend can1 3<DD>#1C70000000000000             # Command 14 VBUS. 답 없으면 15절
python3 tools/can_scan.py                       # 전체 확인
huphy-commission --limb right_leg scan          # 여기서부터 저장소 도구가 붙음
```

cansend can1 1100FD0A#2970000000000000
cansend can1 1900FD0A#0102030405060200

## 13. 응답 한눈에

`candump -x can1` 의 `RX` 줄만 봄. `TX` 는 내가 보낸 에코임.

| 보낸 것 | 정상 응답 | 응답 형식 | 무엇을 뜻하나 |
|---|---|---|---|
| `0000FD<DD>` | `0000<DD>FE` | Type 0 | 그 id 로 모터가 살아 있음 |
| `07<NN>FD<DD>` | `0000<NN>FE` | Type 0 | id 가 `<NN>` 으로 바뀜 |
| `1200FD<DD>` | `0200<DD>FD` | Type 2 피드백 | 파라미터 쓰기가 전달됨 |
| `1600FD<DD>` | `0000<DD>FE` | Type 0 | 저장 명령이 전달됨 |
| `1100FD<DD>` | `1100<DD>FD` | Type 17 | `Byte4` 가 읽은 값 |
| `1900FD<DD>` | `0000<DD>FE` | Type 0 | 전환 명령이 전달됨. 재투입 필요 |
| `<DDD>` (재투입 후) | `0FD` + 상태값 | Response Cmd 1 | **MIT 로 바뀜** |
| `<DDD>#…<HH>01` | `<DDD>` + MCU 고유번호 | Response Cmd 2 | 호스트 id 변경 전달됨. 이 뒤로 응답은 `0<HH>` |
| `3<DD>#<인덱스>…` | `0<HH>` + `<인덱스>0000<값>` | Command 14 응답 | 값은 하위 바이트 먼저. 없으면 구판 펌웨어 |

**응답의 마지막 두 바이트가 요청과 뒤집힘.** 보낼 때는 `<호스트><모터>` 이고 받을
때는 `<모터><호스트>` 임 — Type 0 만 예외로 `<모터>FE` 임.

Type 2 피드백의 `0200` 자리는 모드·고장 비트임. 토크가 켜져 있으면 `0280` 이 됨.

**응답이 왔다 = 명령이 전달됐다** 까지임. 실제로 반영됐는지는 다시 읽어서 봐야 함.

    id        새 id 로 Type 0 를 보내 답하는지
    zero_sta  Type 17 로 읽어 Byte4 가 01 인지
    프로토콜   재투입 후 표준 프레임(3자리)에 답하는지

`RX` 가 아예 없으면 프로토콜 얘기가 아니라 **배선·전원·종단저항** 문제임.

## 14. 호스트 id — Command 9

**모터마다 응답 id 를 다르게 함.** 출하 상태는 모든 모터가 `0x0FD` 로 응답함.

| 공통 id 일 때의 문제 | 결과 |
|---|---|
| 두 모터가 동시에 응답하면 CAN 중재로 못 가름 | 둘 다 깨짐. 그래서 한 모터씩 보내는 `seq` 가 생겼음 ([can_communication.md](can_communication.md) 4절) |
| 파라미터 읽기(Command 14) 응답에는 모터 id 가 없음 | 누구의 값인지 "방금 누구에게 물었나" 로만 알 수 있음 |

id 가 다르면 동시에 응답해도 중재가 정상 동작하고(작은 id 가 먼저, 나머지는 기다림),
응답의 CAN id 만 보고 모터를 앎.

### 규칙 -- `0xF0 + 모터 id`

| 왼다리 (canl) | 호스트 id | 오른다리 (canr) | 호스트 id |
|---|---|---|---|
| 1 hip_pitch | `F1` | 7 hip_pitch | `F7` |
| 2 hip_roll | `F2` | 8 hip_roll | `F8` |
| 3 hip_yaw | `F3` | 9 hip_yaw | `F9` |
| 4 knee | `F4` | 10 knee | `FA` |
| 5 ankle_a | `F5` | 11 ankle_a | `FB` |
| 6 ankle_b | `F6` | 12 ankle_b | `FC` |

이 범위를 고른 이유:

- **명령과 안 겹침.** 호스트 id 는 1바이트라 최대 `0x0FF`. Command 10~15 는 `0x100`
  이상이라 닿지 않음
- **어떤 모터의 id 도 될 수 없음.** 모터 CAN id 는 최대 `0x7F`. 응답 id 가 다른 모터의
  id 와 같으면 그 모터가 응답을 **동작 명령으로 받음** -- `0x80` 이상이면 그럴 일이 없음.
  출하 상태 모터(`0x7F`)를 새로 꽂아도 안전함
- **`FD` 를 비워 둠.** `0FD` 로 응답이 오면 이 설정을 안 한 모터임
- **우선순위.** 숫자가 작은 쪽이 중재에서 이김. 호스트의 명령(`0x001`~)이 응답(`0x0F1`~)
  보다 늘 먼저 나감
- 두 다리는 버스가 따로라 다리 안에서만 안 겹치면 되지만, 모터를 다른 다리로 옮겨 달아도
  되도록 12개를 다 다르게 둠

### 명령

MIT 로 바뀐 뒤(8절)에 보냄.

```bash
cansend can1 <DDD>#FFFFFFFFFFFF<HH>01      # <HH> = F0 + id
cansend can1 00A#FFFFFFFFFFFFFA01          # 무릎(10) -> FA
```

```
can1  TX  00A  [8]  FF FF FF FF FF FF FA 01
can1  RX  00A  [8]  9C 1E 3B C0 00 20 30 0F     <- Response Cmd 2. id 는 모터 id, 데이터는 MCU 고유번호
```

확인은 정지(Command 2)를 보내 **응답의 id** 를 봄.

```bash
cansend can1 00A#FFFFFFFFFFFFFFFD          # RX 0FA ... 이면 됨. 0FD 면 안 됨
```

- **즉시 적용되고 영구임.** 저장 명령(Command 12)이 필요 없음. 전원 재투입·펌웨어
  업데이트 뒤에도 남음 (2026-10-27, 12대 확인)
- 상태 프레임, Command 14 응답, 고장 조회(Command 5) 응답이 **전부** 새 id 로 옴
- 바꾼 직후 **첫 Command 14 는 가끔 답이 없음** (12대 중 4대). 두 번째부터는 정상

## 15. 펌웨어 -- 확인과 업데이트

**Command 12~15(저장·능동 보고·파라미터 읽기·쓰기)는 새 펌웨어에만 있음.** 구판은
아예 답하지 않음.

| 모델 | Command 14 가 되는 판 | 근거 |
|---|---|---|
| RS04 | 0.4.1.29 이상 | 매뉴얼 6.15~6.18절. 0.4.1.24 는 안 됨 (실측) |
| RS03 | 0.3.1.41 이상 (추정) | 같은 배포판(V26.04.07) 기준. 0.3.1.37 은 안 되고 0.3.1.50 은 됨 (실측) |

### 확인

MIT 상태에서 Command 14 에 답하는지 봄. 정확한 버전 숫자는 MIT 로는 못 읽음 (0x1003 이
0 으로 옴) -- private 으로 바꿔야 보임 (`tools/rs_ota.py --info`).

```bash
cansend can1 30A#1C70000000000000          # RX 0FA 1C 70 00 00 <값> 이면 됨. 무응답이면 업데이트
python3 tools/can_scan.py                  # 전체. "Command 14 무응답" 표시가 업데이트 대상
```

### 순서

OTA 는 **private 프로토콜로만** 됨. MIT 모드 모터는 private 프레임에 아예 답하지 않음.
그래서 MIT -> private -> 업데이트 -> MIT 로 돌아옴. 전원 재투입이 두 번 필요함.

```bash
# 1  private 으로 (Command 8, F_CMD=00). 응답은 Response Cmd 2
cansend canr <DDD>#FFFFFFFFFFFF00FD

# 2  전원 재투입 -- 2~3 초 확실히 끌 것

# 3  지금 버전
python3 tools/rs_ota.py --channel canr --motor <id> --info

# 4  기록. 약 10 초. 이 동안 전원을 끄지 말 것
python3 tools/rs_ota.py --channel canr --motor <id> --bin rs03_0.3.1.50.bin

# 5  새 버전 확인 (모터가 다시 뜰 때까지 몇 초 걸림)
python3 tools/rs_ota.py --channel canr --motor <id> --info

# 6  MIT 로 (Type 25). 응답은 0000<DD>FE
cansend canr 1900FD<DD>#0102030405060200

# 7  전원 재투입

# 8  확인 -- 호스트 id 와 Command 14
python3 tools/can_scan.py canr
```

### 업데이트 뒤에 남는 것

CAN id, 호스트 id, zero_sta, 영점이 다 남음. 각도는 업데이트 전후 0~0.1° 차이였음 (5번만
약 2° -- 재투입 중에 발목이 움직인 것으로 봄).

**속도·위치 모드용 기본값은 판마다 다를 수 있음.** 0.4.1.38 로 올린 8번만 `limit_spd`
(0x7017) 20, `spd_kp`(0x701F) 6 이고 구판 RS04 들은 1 / 5 임. MIT 제어에는 안 쓰이는 값임.
RobStride 도 "파라미터를 맞추려면 옛 모터를 최신판으로 올리라" 고 함 (V26.04.07 노트).

### 겪은 것

| 증상 | 원인 / 대처 |
|---|---|
| 재투입했는데 private 으로 안 바뀜 (11번 첫 시도) | 전원이 덜 꺼졌던 것으로 봄. 다시 보내고 확실히 끄니 됨. 모터에 계속 신호를 보내면서 응답이 끊겼다 돌아오는지 보면 정말 꺼졌는지 앎 |
| 재투입 뒤 `canr` 이 `STOPPED` (두 번) | 어댑터가 같이 리셋됨. `huphy-can --channel canr up` (sudo) |
| 기록이 중간에 멈춤 | 겪지 않았음. 매뉴얼 3.3.3절: 실패해도 기존 프로그램은 안 지워짐. 재투입 후 다시 |

RobStride 의 2025-02 배포판 노트는 "RS03·RS04 는 업데이트 뒤 기계 영점을 다시 잡으라" 고
함. 이번(0.3.1.37 -> 0.3.1.50, 0.4.1.24 -> 0.4.1.38)에는 영점이 그대로였지만, 커미셔닝
때 확인할 것.
